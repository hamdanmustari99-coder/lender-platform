### 2.4 SKALA BESAR (pertanyaan 1b — dikalibrasi dgn load test nyata)
Diuji dengan data sintetis di cloud DB yang sama:
- **Dibuat:** 4000 loans (via RPC asli, 40/s) → 12.068 installments, 4.074 cash rows, 1.334 payments.
- **Hasil latency (best of 3):**

| RPC | Data kecil | @4000 loans | Penilaian |
|---|---|---|---|
| list_nasabah (p50) | 300 ms | **943 ms** | Masih OK; bertumbuh linear dgn nasabah, bukan loans |
| setoran_harian p1 | 273 ms | **312 ms** | network jitter; aman |
| setoran_harian p50 | — | **300-an ms** | pagination bekerja |
| kas_harian | 246 ms | **279 ms** | aman |
| laporan_bulanan | 273 ms | **331 ms** | aman (aggregate server-side) |
| REST /loans full fetch (pola Dashboard) | 292 ms | **891 ms, 590 KB** | ⚠ lihat §2.6 |

- **CREATE throughput:** 39–40 loan/detik secara concurrent 10 thread, tanpa error, tanpa deadlock. Cicilan ikut tergenerate 100% (3 per loan).
- **DELETE cascade cleanup:** 11–13 detik per tabel untuk 12k baris — dependensi & index sehat.
- **Kapasitas perkiraan:** dengan profil query yang sekarang, 10 ribu loan terasa normal; 100 ribu loan → semua RPC server-side masih OK, tapi Dashboard pattern harus diganti dulu (§2.6).

### 2.6 PERFORMA & POLA RAWAN (pertanyaan 1d, 1e)

**Yang SUDAH benar (jangan diutak-atik):**
- Semua agregasi uang di Postgres (RPC) — laporan, setoran, kas, list nasabah.
- Paginasi server-side di semua list besar; index lengkap (M20) — idx_pay_paid_at, profiles created_at, composite overdue, dsb.
- N+1 sudah dibunuh sejak M19 (fetchInstallmentsForLoans chunk-200).

**Satu pola RAWAN (prioritas rendah sekarang, wajib sebelum 100rb loan):**
- `Dashboard.tsx` + `Loans.tsx` masih full-fetch **semua** loans (`fetchLoans()` tanpa limit) + Dashboard menarik 2000 payments + 12 profiles + installments — lalu **mengulang seluruh fetch setiap realtime event**.
- Dampak @ 4k loans: latency 891 ms/refresh & payload 590 KB per realtime tick → di 10k loans ~1.5 MB/tick. Gak bikin mati tapi menggerus kuota egress & bikin scroll tidak mulus, plus CPU HP owner.
- **Rekomendasi bertahap:**
  1. (lakukan sekarang, 30 menit) Debounce realtime refetch 3-5 detik di Dashboard/Loans — 1 baris useEffect per halaman.
  2. (sebelum serah terima jika mau rapi, ± 0.5 hari) Ganti Dashboard ke satu RPC `dashboard_ringkasan()` spt pola laporan_bulanan — 4 kartu metrik & daftar harus-siger via server.
  3. (nanti kalau nasabah > 5k) Loans list pindah ke RPC paginasi + search server-side seperti users.

### 2.7 SECURITY HARDENING (mitigasi, bukan penemuan)
**Web:**
- RLS anon read: semua 11 tabel → EMPTY ✅ · anon write → 401 ✅
- Edge function `danaku-api`: no-auth → 401, anon-as-bearer → 401 "Token tidak valid" ✅; role cek di server; password nasabah random per-akun (account wadah tanpa login).
- npm audit: **0 critical / 0 high / 0 moderate / 0 low.**
- Secret scan bundle `admin/dist`: tidak ada service_role/secret/token JWT; hanya URL + anon key (by design publik).
- Konfirmasi `admin/server/.env` (service_role + Cloudinary secrets) tidak pernah diimport oleh frontend (hanya di-render-server untuk proxy upload).

**Desktop (Electron):**
- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: false` (butuh preload fs; layanan akan di-allowlist kalau nanti perlu).
- **Navigation lock baru:** `will-navigate` dibatasi `file://` + `devtools://`; navigasi lain dibatalkan + openExternal. `will-attach-webview` ditolak total.
- **Permission handler baru:** semua request permission (kamera, notifikasi, lokasi) default-deny.
- Secret (Supabase URL + anon key) dibaca runtime dari `../admin/.env` via `sendSync` — tidak di-bundle ke aplikasi (verified secret scan dist desktop = bersih).
- Rebuilt dengan hardening: `SWFinance-Setup-1.0.0.exe` (überschrieben 7 Nov, 01:36).

**Mobile:** TIDAK ADA — aplikasi mobile Flutter dihapus total di M21 dan jenazah build-nya dianggap tidak ada; upaya sebelumnya (mobile/) adalah arsip build yang tidak digunakan. Tidak ada yang perlu di-harden di front ini.
